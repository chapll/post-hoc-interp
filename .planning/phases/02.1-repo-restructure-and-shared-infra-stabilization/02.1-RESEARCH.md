# Phase 2.1: Repo Restructure and Shared Infra Stabilization - Research

**Researched:** 2026-02-06
**Domain:** Python package structure, import system, project reorganization
**Confidence:** HIGH

## Summary

This phase is a structural move, not a rewrite. All research-active code lives in `src/experimental/gorn/` and must be promoted to the main repo. The original training infrastructure in `src/infra/` is already backed up in `archive/` and is not needed for the current research direction.

The core challenge is import path management. The gorn scripts currently use two different import patterns: three scripts (generate_traces.py, capture_activations.py, validate.py) use `sys.path.insert(0, "src/experimental/gorn")` plus `from lib.X import Y`, while two newer scripts (check_traces.py, verify_phase2.py) use absolute package imports like `from src.experimental.gorn.lib.config import load_config`. Additionally, the config loader (`lib/config.py`) uses `Path(__file__).resolve().parent.parent / "configs"` to find YAML configs relative to its own filesystem location, which will break when the file moves.

**Primary recommendation:** Replace `src/infra/` contents with gorn's `lib/` modules, move scripts to top-level `scripts/`, update all imports to use `from src.infra.X import Y` absolute package imports, update config path resolution to use a project-root-relative approach, and move gorn's configs to the top-level `configs/` directory (replacing the old Hydra configs).

### Pattern 1: Absolute Package Imports

**What:** All scripts import from the installed `src` package using absolute paths.
**When to use:** Every import of shared infra modules.
**Why:** The project uses `packages = ["src"]` in hatchling config and is installed editable via `uv`. This means `import src.infra.X` works from anywhere without `sys.path` hacks.

After restructure, all imports become:
```python
from src.infra.config import load_config
from src.infra.model import load_model, generate_trace
from src.infra.multiprocess import run_parallel_isolated
from src.infra.storage import save_trace, get_activation_path
from src.infra.tokens import parse_think_boundaries
from src.infra.utils import set_seed, setup_logging
```

This eliminates all `sys.path.insert()` calls and all `from lib.X` relative imports.

### Pattern 2: Config Path Resolution via Project Root

**What:** Instead of `Path(__file__).resolve().parent.parent / "configs"`, use an explicit project-root discovery.
**Why:** The current config loader in `lib/config.py` line 15 does:
```python
_CONFIGS_DIR = Path(__file__).resolve().parent.parent / "configs"
```
This navigates from `lib/config.py` -> `lib/` -> `gorn/` -> `gorn/configs/`. After moving `config.py` to `src/infra/config.py`, `parent.parent` would resolve to `src/`, which is wrong.

**Solution:** Use project root discovery. Two options:

**Option A (recommended): Find project root by locating pyproject.toml**
```python
def _find_project_root() -> Path:
    """Walk up from this file to find the directory containing pyproject.toml."""
    current = Path(__file__).resolve().parent
    while current != current.parent:
        if (current / "pyproject.toml").exists():
            return current
        current = current.parent
    raise FileNotFoundError("Could not find project root (no pyproject.toml found)")

_CONFIGS_DIR = _find_project_root() / "configs"
```

**Option B: Hardcode relative navigation**
```python
# src/infra/config.py -> src/infra/ -> src/ -> project_root/ -> configs/
_CONFIGS_DIR = Path(__file__).resolve().parent.parent.parent / "configs"
```

Option A is more robust and survives future moves. Option B is simpler but brittle.

### Pattern 3: Script Invocation After Restructure

**What:** Scripts move from `src/experimental/gorn/scripts/` to top-level `scripts/`.
**Invocation changes:**

Before:
```bash
uv run python src/experimental/gorn/scripts/generate_traces.py \
    --config src/experimental/gorn/configs/generate.yaml --gpus 0,1,2,3
```

After:
```bash
uv run python scripts/generate_traces.py \
    --config configs/generate.yaml --gpus 0,1,2,3
```

Scripts no longer need `sys.path.insert()` because `src` is an installed package (via `uv pip install -e .` or equivalent).

### Anti-Patterns to Avoid

- **sys.path.insert hacks:** Three scripts currently use `sys.path.insert(0, "src/experimental/gorn")` to make `from lib.X` work. This is fragile and breaks when cwd changes. Absolute package imports eliminate this entirely.
- **Relative imports from `lib.`:** These only work when `sys.path` includes the gorn directory. After restructure, use `from src.infra.X`.
- **`__file__`-relative config paths without robustness:** The check_traces.py script (line 358) does `Path(__file__).resolve().parent.parent / "configs" / "generate.yaml"`. After moving to `scripts/`, `parent.parent` would be the project root -- this happens to work if configs/ is at project root, but it should use the same config loader as everything else, not ad-hoc path construction.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Package import resolution | sys.path manipulation | hatchling `packages = ["src"]` + `uv` editable install | sys.path hacks break when cwd changes, in subprocesses, or in tests |
| Config file discovery | Multiple ad-hoc `Path(__file__)` navigations | Single `_find_project_root()` helper in config.py | One place to maintain, survives any future moves |
| Bulk import updates | Manual find-and-replace | `sed` or scripted replacement | There are exactly 33 `from lib.` import lines plus 3 `sys.path.insert` lines to update |

## Common Pitfalls

### Pitfall 1: Missing `__init__.py` Files

**What goes wrong:** After moving files, `from src.infra.config import load_config` raises `ModuleNotFoundError` because Python doesn't recognize `src/` or `src/infra/` as packages.
**Why it happens:** Currently there are NO `__init__.py` files in `src/`, `src/infra/`, or `src/models/`. The only `__init__.py` files are in `gorn/lib/` and `gorn/scripts/` (both empty).
**How to avoid:** Create `__init__.py` in both `src/` and `src/infra/` as part of the move. They can be empty files.
**Warning signs:** Any `ModuleNotFoundError: No module named 'src'` or `No module named 'src.infra'`.

### Pitfall 2: Config Path Resolution Breaks Silently

**What goes wrong:** `config.py` uses `Path(__file__).resolve().parent.parent / "configs"` to find `base.yaml`. After moving to `src/infra/config.py`, parent.parent resolves to `src/` instead of the gorn directory, so it looks for `src/configs/base.yaml` which does not exist.
**Why it happens:** Filesystem-relative path resolution is tied to the file's physical location.
**How to avoid:** Update the config path resolution before or simultaneously with the file move. Test that `load_config()` can find `base.yaml` immediately after the move.
**Warning signs:** `FileNotFoundError: Base config not found at /path/to/src/configs/base.yaml`.

### Pitfall 3: Data Path References in YAML Configs

**What goes wrong:** The YAML configs contain hardcoded paths like `data_dir: "src/experimental/gorn/data"`, `traces_dir: "src/experimental/gorn/data/traces"`, `activations_dir: "src/experimental/gorn/data/activations"`. After restructure, these paths are wrong.
**Why it happens:** Config values reference the old directory structure.
**How to avoid:** Update all path values in the YAML configs to use the new layout (e.g., `data_dir: "data"`, `traces_dir: "data/traces"`).
**Files affected:**
- `base.yaml` lines 30-31: `data_dir` and `experiments_dir`
- `capture.yaml` lines 13-14: `traces_dir` and `activations_dir`
- `generate.yaml` line 22: `traces_dir`

### Pitfall 4: Subprocess Import Context

**What goes wrong:** Scripts that use `run_parallel_isolated()` spawn new processes via `mp.get_context("spawn")`. The spawned processes need `src` to be importable. If the editable install is not active in the spawned process, imports fail.
**Why it happens:** `mp.spawn` (via `torch.multiprocessing`) inherits the parent process's Python path, but `mp.Process` with the "spawn" context starts fresh. However, since `uv run` sets up the virtualenv with the editable install, `src` should be available as an installed package.
**How to avoid:** Verify that after restructure, spawned worker processes can `from src.infra.model import load_model` without any `sys.path` manipulation. The current `sys.path.insert` approach is actually fragile here -- the absolute import approach is MORE reliable for subprocesses.
**Warning signs:** Workers failing with `ModuleNotFoundError` in multi-GPU scripts.

### Pitfall 5: .gitignore Data Path Needs Updating

**What goes wrong:** The `.gitignore` contains `src/experimental/gorn/data/` (line 31) to exclude data files. After restructure, data moves to `data/` at project root, but the gitignore still points to the old path.
**Why it happens:** Gitignore paths are not updated during the move.
**How to avoid:** Update `.gitignore` to add `data/` and remove the old `src/experimental/gorn/data/` entry. Also update the `!src/experimental/gorn/lib/` exception on line 18 (no longer needed since we're removing the `lib/` gitignore exclusion path).

### Pitfall 6: check_traces.py Has Its Own Ad-Hoc Config Loading

**What goes wrong:** `check_traces.py` (line 357-360) constructs a config path using `Path(__file__).resolve().parent.parent / "configs" / "generate.yaml"` instead of using CLI arguments. This is a separate path resolution from `config.py` and must be updated independently.
**Why it happens:** This script was written to auto-discover its config file relative to its own location.
**How to avoid:** After moving to `scripts/check_traces.py`, update this path to use the same config discovery mechanism. Since `parent.parent` from `scripts/check_traces.py` would be the project root, and configs move to `configs/` at project root, this actually resolves correctly by accident -- but it should still be converted to use `load_config()` properly for consistency.

### Pitfall 7: Entry Point and Old Code References

**What goes wrong:** `pyproject.toml` defines `train = "src.train:main"` as a console script entry point. After removing `src/train.py`, this entry point breaks.
**Why it happens:** The old training code is being eliminated but the entry point is not removed.
**How to avoid:** Remove the `[project.scripts]` section from `pyproject.toml` (or replace with new entry points for the pipeline scripts). Also remove `src/config.py` and `src/models/mlp.py` which are only used by the old training system.

## Detailed Conflict Analysis

### Q3: gorn's utils.py vs existing src/infra/utils.py -- Conflict Assessment

**Finding: ZERO functional overlap. Complete replacement is safe.**

| Function | gorn's lib/utils.py | Old src/infra/utils.py |
|----------|--------------------|-----------------------|
| `set_seed()` / `set_random_seed()` | Rejects seed=42, sets `benchmark=False` | Allows any seed, sets `benchmark=True` |
| `get_device()` | Returns `torch.device` for GPU, no CPU fallback | Not present |
| `setup_logging()` | Plain text logger to stdout | Not present |
| `TimedContext` | Not present | Context manager for timing |
| `get_time()` | Not present | Cached datetime |
| `get_num_params()` | Not present | Param counting for models |
| `GarbageCollection` | Not present | Scheduled GC for training |

The old `src/infra/utils.py` is entirely training-focused (timing, GC management, param counting). gorn's `utils.py` is entirely inference-focused (seeding, device selection, logging). Since the old training infra is being eliminated, gorn's utils.py simply replaces it completely. No merging needed.

### Q4: gorn's configs/ vs top-level configs/ -- Config System Conflict

**Finding: Complete replacement. Different config systems, no overlap.**

The top-level `configs/` directory contains Hydra-structured configs (14 YAML files across subdirectories: `checkpoint/`, `comm/`, `config.yaml`, `deploy/`, `experiment/`, `job/`, `model/`, `parallelism/`, `training/`, `wandb/`). These are used exclusively by `src/train.py` via `@hydra.main()`.

gorn's `configs/` contains OmegaConf-direct configs (4 YAML files: `base.yaml`, `capture.yaml`, `generate.yaml`, `validate.yaml`). These are loaded via the custom `load_config()` function.

Since the old training system is being eliminated, the Hydra configs are dead code. Replace the entire `configs/` directory contents with gorn's configs.

## Testing Strategy

### What to Test for Shared Infra Modules

For GPU-dependent research code, the testing strategy must be practical: not everything can run in CI, but critical paths must be verified.

**Tier 1: Unit tests (no GPU required, run in CI)**

| Module | Test Focus | GPU? |
|--------|-----------|------|
| `config.py` | load_config() finds base.yaml, merges script configs, applies CLI overrides | No |
| `datasets.py` | Balance checking, schema validation, distractor generation (requires HuggingFace download) | No |
| `prompts.py` | Prompt construction for all 3 datasets, swapped-label protocol A/B | No |
| `storage.py` | save/load round-trip with safetensors, path helpers, atomic write, derive_trace_seed | No |
| `tokens.py` | parse_think_boundaries, content masks, pre-handoff window with synthetic token sequences | No |
| `utils.py` | set_seed rejection of 42, setup_logging | No |
| `multiprocess.py` | split_work correctness, edge cases (0 items, more workers than items) | No |

**Tier 2: Integration tests (GPU required, run manually)**

| Test | What It Validates |
|------|-------------------|
| `scripts/validate.py` | Full pipeline: load config, load datasets, load model, generate trace, capture activations, storage round-trip, multi-GPU |
| Import smoke test | `from src.infra.config import load_config` works from any directory |
| Subprocess import test | Spawned `mp.Process` can `from src.infra.model import load_model` |

**Testing patterns for this kind of code:**

1. **Synthetic token sequences for tokens.py:** Create lists of ints with known THINK_TOKEN_ID (151667) and THINK_END_TOKEN_ID (151668) positions. No GPU needed.
2. **Temporary directories for storage.py:** Use `tempfile.TemporaryDirectory` for safetensors round-trip tests.
3. **Mock-free config tests:** Create temp YAML files, call `load_config(script_config=path)`, verify merged result.
4. **pytest as test runner:** The project already has pytest available. Use `tests/` directory at project root.

## Open Questions

### 1. Should `data/` stay at project root or remain under `src/`?

**What we know:** Currently data lives at `src/experimental/gorn/data/` (gitignored). The YAML configs reference this path. Moving it to project-root `data/` is cleaner and matches convention.
**What's unclear:** Whether existing data on disk needs to be moved or just the config path references updated. If data already exists at `src/experimental/gorn/data/`, moving it could break in-progress work.
**Recommendation:** Update config path references to `data/` at project root. If data already exists at the old path, either `mv` it or create a symlink. The planner should include a task for this but flag it as "check if data exists before moving."

### 2. Should the `configs/` directory keep old Hydra configs as archive?

**What we know:** The old Hydra configs (14 files across subdirectories) are only used by `src/train.py` which is being removed. They are already preserved in `archive/configs/`.
**Recommendation:** Remove all old Hydra config subdirectories from `configs/` and replace with gorn's 4 OmegaConf YAML files. The archive already has the backup.

### 3. Should `src/experimental/` be completely deleted or just emptied?

**What we know:** The user explicitly said "the experimental directory concept is being eliminated entirely." After promoting gorn's code, `src/experimental/ali/` and `src/experimental/eric/` contain only README.md files.
**Recommendation:** Delete `src/experimental/` entirely. Ali and Eric can create new experiment directories when needed, or work directly with the shared infra via imports.

### 4. Should new entry points be added to pyproject.toml?

**What we know:** The old `train = "src.train:main"` entry point will be removed. The scripts are currently run via `uv run python scripts/X.py`.
**Recommendation:** Do NOT add new entry points in this phase. The `uv run python scripts/X.py` pattern is explicit and familiar. Entry points can be added later if the team wants `uv run generate-traces` style commands.
