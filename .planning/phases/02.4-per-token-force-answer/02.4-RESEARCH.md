# Phase 2.4: Per-Token Force-Answer Probing - Research

**Researched:** 2026-02-26
**Domain:** KV-cache-efficient dense probing of a single LLM reasoning trace
**Confidence:** HIGH

## Summary

This phase extends the ~20-point force-answer probing from Phases 2.2/2.3 to every-token resolution on a single representative trace (`gsm_symbolic_68_fresh_false_cfga`). The existing probing infrastructure in `scripts/force_answer_experiment.py` -- specifically the `probe_trace()` function, `extract_answer()`, `extract_rho_tau_probs()`, and the KV-cache descending-order strategy with `DynamicCache.crop()` -- is fully reusable. The main work is: (1) a new experiment script that loads one trace, generates all 824 probe positions (instead of ~20 evenly-spaced), runs them through the existing probing logic, and saves results; (2) a plotting script that generates high-resolution curves and overlays the Phase 2.2 coarse grid for comparison.

The target trace has 824 thinking content tokens (indices 0-823 relative to think content start, think boundaries [103, 928] in absolute token space). Phase 2.2 probed this trace at 20 evenly-spaced positions and showed an interesting non-monotonic transition: accuracy jumps to True at position 346 (42% through thinking), oscillates in the middle, and stabilizes at True around position 693 (84%). The per-token probing will reveal whether this oscillation is a real phenomenon or an artifact of the coarse grid, and pinpoint the exact token-level dynamics.

Computationally, 824 probes with `max_new_tokens=15` on a single GPU should take 4-14 minutes depending on per-probe latency. The KV-cache strategy (prefill once, crop in descending order) makes this feasible without 824 full forward passes.

**Primary recommendation:** Create a lean single-trace experiment script that reuses `probe_trace()` from `force_answer_experiment.py` with a modified config that sets `num_probes` to the think block length, plus a dedicated plotting script that generates the high-resolution curve and overlays Phase 2.2 data.

### Pattern 1: Single-Trace Dense Probing via cfg_shim

**What:** Load one specific trace by problem_id and trace_index, generate all probe positions (not evenly-spaced), use `probe_trace()` with a cfg_shim that sets `num_probes` equal to the think content length and `min_probe_spacing=1`.

**When to use:** When probing a single trace at every token position.

**How it works:**
- The existing `compute_probe_positions(think_length, num_probes, min_spacing)` function in `force_answer_experiment.py` already returns evenly-spaced positions. When `num_probes >= think_length` and `min_spacing=1`, it returns `np.linspace(0, think_length-1, think_length)` which is every position 0 through think_length-1.
- The `probe_trace()` function already handles descending-order KV cache processing.
- A cfg_shim with `force_answer.num_probes = <think_length>` and `force_answer.min_probe_spacing = 1` will produce all positions.

**Example:**
```python
# Source: scripts/cross_seed_experiment.py (cfg_shim pattern)
from omegaconf import OmegaConf

cfg_shim = OmegaConf.create({
    "force_answer": {
        "num_probes": think_length,       # 824 for this trace
        "min_probe_spacing": 1,           # every token
        "max_new_tokens": 15,             # same as Phase 2.2
    }
})

results = probe_trace(raw_model, tokenizer, trace_data, cfg_shim, device)
```

### Anti-Patterns to Avoid

- **Using `load_traces_for_experiment()` for single-trace loading:** That function does dataset-balanced random selection. For one specific trace, load it directly by path.
- **Using multi-GPU for a single trace:** Only one trace, no work to distribute. Run on a single GPU for simplicity.
- **Setting `num_probes` very high without setting `min_probe_spacing=1`:** The `compute_probe_positions()` function caps probes at `think_length // min_spacing`. If `min_spacing` is the default 5, maximum probes would be 164, not 824.
- **Re-implementing probing logic:** Import from `force_answer_experiment.py` as the single source of truth (following Phase 2.3 pattern).
- **Ascending-order probing:** Must process in descending order for cache cropping efficiency. `probe_trace()` already does this.

## Common Pitfalls

### Pitfall 1: min_probe_spacing Not Set to 1
**What goes wrong:** `compute_probe_positions(824, 824, min_spacing=5)` returns at most 164 positions (824 // 5), not 824.
**Why it happens:** Default `min_probe_spacing` in the config is 5 (from Phase 2.2 where ~20 evenly-spaced points was the goal).
**How to avoid:** Explicitly set `min_probe_spacing: 1` in the per_token_probe.yaml config and verify the returned positions list has length == think_length.
**Warning signs:** Results parquet has fewer rows than expected (check `len(results) == 824`).

### Pitfall 2: Memory Accumulation Over 824 Probes
**What goes wrong:** Each `probe_trace()` call with `copy.deepcopy(cache)` creates a cache copy. The generate() output objects accumulate logits tensors. Over 824 iterations, GPU memory may grow.
**Why it happens:** PyTorch/transformers may not immediately free tensors from previous generate() calls.
**How to avoid:** Call `torch.cuda.empty_cache()` periodically (e.g., every 100 probes) and monitor GPU memory. The existing `probe_trace()` function already handles cache management -- this is more about the caller ensuring cleanup after the function returns.
**Warning signs:** Gradual GPU memory increase visible via `nvidia-smi`, eventual OOM.

### Pitfall 3: Confusing Absolute vs Relative Probe Positions
**What goes wrong:** The `probe_position` column stores positions relative to think content start (0-indexed), but the trace's absolute token indices start from the prompt. Plotting against absolute indices would misalign with Phase 2.2 data.
**Why it happens:** Phase 2.2 results also use relative positions (0-indexed from think content start), but if someone tries to correlate with the token_ids array, they need to add `think_start + 1` offset.
**How to avoid:** Always plot against `probe_position` (relative) or `normalized_position` for consistency with Phase 2.2. Document the offset in the results summary JSON.
**Warning signs:** Phase 2.2 overlay doesn't align with per-token data.

### Pitfall 4: probe_trace() Returns Empty List for Zero-Length Think Block
**What goes wrong:** If somehow the trace metadata is malformed and `think_length <= 0`, `probe_trace()` returns an empty list silently.
**Why it happens:** Guard clause in `probe_trace()`.
**How to avoid:** Validate think_length (should be 824 for this trace) before calling probe_trace(). Fail loudly if unexpected.
**Warning signs:** Results parquet is empty.

### Pitfall 5: Output Format Mismatch Between JSON and Parquet
**What goes wrong:** The roadmap says "results saved as structured JSON" but the Phase 2.2/2.3 pattern uses parquet.
**Why it happens:** The success criterion says "structured JSON" but the codebase consistently uses parquet for tabular data.
**How to avoid:** Save as both: parquet for the tabular per-position data (consistent with 2.2/2.3), and a JSON summary with metadata and aggregate statistics.
**Warning signs:** Downstream consumers can't find results in expected format.

## Code Examples

### Loading a Single Trace
```python
# Source: scripts/force_answer_experiment.py (trace loading logic)
import json
import os

def load_single_trace(traces_dir, problem_id, dataset, trace_index=0):
    """Load a single specific trace by problem_id."""
    trace_path = os.path.join(
        traces_dir, "valid", dataset, problem_id,
        f"trace_{trace_index:02d}.json"
    )
    with open(trace_path) as f:
        trace = json.load(f)

    meta = trace["metadata"]
    # Determine correctness for this trace
    ground_truth = meta["ground_truth"]
    valid_token = meta["valid_token"]
    invalid_token = meta["invalid_token"]
    expected_token = valid_token if ground_truth == "Yes" else invalid_token

    generated_text = trace.get("generated_text", "")
    think_end_idx = generated_text.rfind("</think>")
    answer_text = generated_text[think_end_idx:] if think_end_idx >= 0 else generated_text
    is_correct = expected_token.lower() in answer_text.lower()

    return {
        "trace_path": trace_path,
        "token_ids": trace["token_ids"],
        "metadata": meta,
        "is_correct": is_correct,
        "dataset": dataset,
    }
```

        df_coarse["normalized_position"],

    # Same for probability panel
    ax_prob.plot(
        df_dense["normalized_position"],
        df_dense["correct_token_prob"],
        color=PROB_COLOR, linewidth=0.8, alpha=0.8,

## Computational Feasibility

| Aspect | Value |
|--------|-------|
| Probes needed | 824 |
| Per-probe cost | ~0.3-1.0s (generate 15 tokens greedy) |
| Estimated total time | 4-14 minutes on single GPU |
| KV cache strategy | Prefill once (full 932 tokens), crop in descending order |
| Memory per probe | Deepcopy of KV cache + generate output (~small per probe) |
| GPUs needed | 1 (single trace, no parallelism benefit) |
| Model | Qwen3-8B in BF16 (~16 GB VRAM) |

The KV-cache strategy means:
1. One full forward pass to build the cache (932 tokens)
2. For probe at position 823 (last): crop to 927 tokens, deepcopy, generate
3. For probe at position 822: crop to 926 tokens from same cache, deepcopy, generate
4. ...down to position 0: crop to 104 tokens, deepcopy, generate

This is already implemented in `probe_trace()` -- no new code needed for cache management.

## Open Questions

1. **Whether `probe_trace()` can handle 824 positions without memory issues**
   - What we know: It works for 20 positions per trace. The descending-order cache cropping is correct.
   - What's unclear: Whether 824 iterations of deepcopy + generate accumulate enough memory to cause OOM.
   - Recommendation: Add periodic `torch.cuda.empty_cache()` calls and monitor memory. If OOM occurs, process in batches of ~200 positions with cache re-prefill between batches. But this is unlikely given that each probe generates only 15 tokens.

2. **Whether the results format should be JSON or parquet**
   - What we know: Success Criterion 1 says "structured JSON" but Phase 2.2/2.3 use parquet consistently.
   - Recommendation: Save as parquet (primary, consistent with codebase) AND a JSON summary with metadata. The JSON summary should contain: problem_id, think_length, num_probes, transition characterization, and aggregate statistics.

3. **What "transition characterization" means concretely**
   - What we know: Success Criterion 4 asks for "characterization of transition shape (step function, ramp, oscillatory, etc.)."
   - Recommendation: Compute simple metrics on the per-token accuracy curve: (a) number of correct-to-incorrect and incorrect-to-correct transitions, (b) longest run of consecutive correct/incorrect, (c) first position reaching sustained correctness (e.g., 5 consecutive correct), (d) probability variance in the middle region. Report these in the JSON summary. The plots themselves are the primary characterization tool.
